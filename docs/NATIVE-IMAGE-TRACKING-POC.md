# 本尊鸿蒙原生图片追踪原型

更新日期：2026-10-26。开发分支：codex/harmony-kivicube。

## 当前结论

用户已在鸿蒙微信预览版确认原生相机实时画面、RGBA 有效帧计数持续增长，以及 WebGL 绿色画布显示。确认的是基础能力，不是完整 AR。

本次新增无服务器的本尊图片定位原型：camera 帧 → 本地 ORB 特征匹配 → 单应矩阵几何验证 → WebGL 取帧预览及绿色四边框。没有使用 VisionKit、收费 SDK、远端识别或宿主 web-view。

用户已在鸿蒙真机确认图片定位：绿框贴合识别图，移动、倾斜、移开后重新扫描正常。随后截图显示匹配 49、几何内点 44、单次完整识别 188 ms，并反馈画面明显卡顿。图片定位可行性已取得真机证据，性能仍未通过；没有加载 3D 模型、动画和讲解，也没有宣称最终鸿蒙 AR 兼容问题已解决。

## 真机操作

1. 使用本分支最新工程重新编译，生成开发版预览或体验版。
2. 在目标鸿蒙微信进入模型选择页，点击“本尊原生图片追踪”。该入口只在开发版/体验版显示。
3. 在电脑或另一台设备打开 recovery-assets/cards/tssgd.jpg，保持原图宽高比，不只显示截图中的局部。
4. 点击“开始图片追踪”并允许相机。上方是原生相机预览，下方是算法处理的实际取帧画面。当前边框画在下方画面，不是叠加 3D 的正式 AR 界面。
5. 先正对识别图并让图占较大画面，再轻微倾斜和移动。观察下方是否出现贴合完整识别图的绿色边框及四个角点。
6. 移开识别图应不再显示边框，重新移入应恢复定位。匹配数量增加本身不代表检测成功，必须看到正确的几何定位。
7. 截图反馈下方取帧方向、绿框位置、匹配数、几何内点、处理模式、单次处理毫秒数，以及实际预览帧率/定位频率。分别记录“完整识别”和“连续追踪”，不能用连续追踪的一帧耗时代表完整识别的耗时。记录手机型号、HarmonyOS 和微信版本，以区分机型差异。

画面仅在设备内处理，不保存、不上传。停止、离开页面和进入后台均释放取帧监听，防止旧会话回调污染新会话。

## 离线验证

使用本尊原图经独立变换构造 480×640 测试画面：缩放平移、15°旋转、90°旋转、透视、非目标帧后重新识别；校验投影四角与已知真值的最大误差小于 10 像素。最后一次本机运行各正例误差约 1.03～3.21 像素。

负例覆盖空白、确定性噪声、一张工程内无关图片，以及错误长度帧。没有将这些少量测试外推为所有场景的误识别率。检测耗时是在本机 Node 环境测得，不能作为鸿蒙手机帧率承诺。

几何估计采用固定工作上限、根据匹配数据初始化的本地采样序列以及局部重估，避免通用随机估计器在该卡片上因退化点组提前退出；相同输入的结果可复现。图像处理复用角点缓冲，并限制检测分辨率及处理频率，实际手机性能待测。

主模型仍未加入本原型，图片特征和识别库均随测试分包本地加载；最终体积以微信打包报告为准。

### 流畅度优化（真机复测待完成）

- 旧版每帧完整识别，再等待至少 250 ms，且只在完整识别后更新预览。188 ms 的识别计算加等待已是至少 438 ms 一轮，尚不含绘制等开销。
- 新增 session-tracker.js：完整 ORB 识别后保留已验证的特征对应关系，使用长边最多 320 像素、最多 48 点的三级金字塔 LK 光流，执行前后向一致性、亮度变化容忍的局部贴片比较和单应矩阵验证。
- 连续追踪对照最近一次完整识别的关键帧，避免逐帧累积漂移。最多 2 秒重新进行一次完整识别；画面变化太大、目标丢失、回调间隔超过 500 ms、相机尺寸改变以及停止重启都会丢弃旧追踪。丢失时立即清除边框，下一次处理重新识别。
- 连续定位按帧到达时间安排约 80 ms 的最小处理间隔；未定位时完整识别间隔约 400 ms。预览单独安排至少 50 ms 的刷新间隔，等待识别的间隙仍可刷新。跳过定位计算的画面最多沿用 160 ms 内的边框；状态文字更新节流至约 500 ms，模式/定位状态改变时立即更新。
- 页面显示最近约一秒的实际预览帧率及定位处理频率，均为实测计数，不是固定的帧率承诺。
- 41 个合成目标帧测试通过，其中 34 帧走连续追踪，最大四角误差约 7.58 像素（要求仍为小于 10 像素）。另覆盖目标消失、无关图、亮度变化、定期完整识别、长间隔、停止重置及相机尺寸变化；页面模拟测试确认预览可在两次完整识别之间刷新、失败后不保留旧框、停止后旧回调无效。

计算仍同步运行在小程序逻辑线程，完整识别和定期复核仍可能造成短暂停顿。预览与识别调度已拆开，但不等于算法已转到后台线程。PC 离线耗时不能证明鸿蒙实际帧率，也不能保证叠加 3D 后仍流畅。下一步应先用同一台手机复测该优化版，记录连续追踪耗时、帧率及绿框稳定性，再决定是否需要工作线程等进一步优化。

## 重建与测试

需要 Pillow 的 Python 环境，运行 recovery-tools/prepare-native-target.py 生成临时的 640 像素上限 RGBA 参考图及尺寸 JSON。默认输出系统临时目录 ysj-native-target.rgba / ysj-native-target.json。

随后运行：

```text
node recovery-tools/train-native-target.cjs <参考图.rgba> <尺寸.json>
node recovery-tools/test-native-tracker.cjs <参考图.rgba> [480×640无关图片.rgba]
node recovery-tools/test-native-session.cjs <参考图.rgba> [480×640无关图片.rgba]
node recovery-tools/test-native-page.cjs
```

特征文件 pages/ar-native-track/target.js 已生成，可直接编译预览，无需用户手机执行训练。当前参考图尺寸 427×640，包含 602 个多尺度特征。

### 页面空白修复（2026-10-26）

用户反馈点击“本尊原生图片追踪”后页面空白。检查发现页面注册前直接 require("./target.json")，误用了 Node 的 JSON 模块加载能力。现改为 target.js 导出相同特征数据，同步修正训练脚本及离线测试引用；依赖初始化放在页面注册后的 onLoad 中捕获错误，画布查询同步异常也会显示在状态文字中。

新增 `node recovery-tools/test-native-page.cjs`，以仅加载 JS、不提供浏览器全局对象的模块环境验证页面注册、真实依赖加载及依赖失败时的可见错误。该检查能够复现旧代码在 Page 注册前中断的问题。修复后需清理开发者工具缓存并重新编译生成新的预览码，在鸿蒙真机复核；不能把离线启动测试当作真机通过。

工程检查还覆盖页面启动停止、旧监听回调隔离、后台释放及画布资源释放。JSON、JS、WXML、本地依赖和素材引用检查通过。

## 下一步

图片定位已由用户真机验证，但旧版明显卡顿。先复测本次连续追踪和独立预览调度的性能及稳定性；通过后再校准相机内参/姿态和画布映射，接一个本尊墨玉模型。模型贴合稳定后逐项加入动画、音频及六套业务场景。不能把二维码识别成功或有图像特征匹配当成稳定的 3D AR 验收。

Kivicube 因超预算排除，云服务器不作为本轮验证前提。共创 AR 网页二维码继续作为备用；原有 Android/iOS 业务入口保留。
